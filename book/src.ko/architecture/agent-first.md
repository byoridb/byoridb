# Agent-first 제품 설계

[English](../../architecture/agent-first.html) | **한국어**

ByoriDB는 관계를 이해하고, 도출 근거를 확인하며, 상태의 일관성을 유지해야 하는
에이전트를 위해 설계합니다. 엔진은 범용 그래프·온톨로지 데이터베이스로 유지합니다.
Agent memory, 의존성 분석, 지식 카탈로그는 그 위의 응용 프로필입니다.

**상태: 채택한 제품 방향이며 구현은 단계적으로 제공합니다.**
기준 문서인 [제품 설계](https://github.com/byoridb/byoridb/blob/main/docs/PRODUCT_DESIGN.ko.md)는
목표 계약을 정의하고, [로드맵](../development/roadmap.html)은 수용·개발 상태를 추적합니다.
현재 호출할 수 있는 기능은 [API 레퍼런스](../reference/api.html)에 명시합니다.
아래 흐름은 실행 가능한 API가 아닌 설계입니다.

## 주 상호작용

```text
Discover -> Query -> Inspect evidence -> Prepare change -> Apply -> Verify
    ^          |             |                 |            |        |
    +----------+-------------+-----------------+------------+--------+
          explicit errors, bounded results, outcome recovery
```

각 단계는 다음 책임을 갖습니다.

| 단계 | 목표 동작 |
|---|---|
| Discover | 인가된 스키마와 사용 가능한 연산만 타입·버전·상한·예제와 함께 반환 |
| Query | 타입 있는 인자를 받고 완전성·일관성 범위를 명시한 크기 제한 결과 반환 |
| Inspect evidence | asserted data, 도출 규칙·전제, 출처, 알 수 없는 근거를 구분 |
| Prepare change | 변경을 검증하고 미리보기를 요청·범위·관련 revision에 연결 |
| Apply | 권한·전제조건 재검사 후 공표한 원자적 경계 안에서 commit하고 연산 결과 기록 |
| Verify | 응답 유실 뒤 기록된 결과를 조회해 무작정 변경을 다시 요청하지 않고 상태 확인 |

에이전트는 작업을 계획하고 행동을 선택합니다. ByoriDB는 타입·제약·접근 권한·실행
상한·공표한 데이터 보장을 강제합니다. 사람은 credential을 발급하고 근거·변경을
검토하며 서비스를 복구합니다. 미리보기는 권한을 부여하지 않으며 도구 설명은 접근 제어
수단이 아닙니다.

## 근거와 불확실성

추론 설명은 저장된 전제와 지원하는 규칙에서 결론이 어떻게 도출됐는지를 보여 줍니다.
asserted fact가 현실에서 참이라는 증거는 아닙니다. 출처와 논리적 도출 근거를
구분해야 합니다. LLM이 생성한 주장은 저장되거나 인용됐다는 이유만으로 검증된 사실이
되어서는 안 됩니다.

빈 결과는 특정 범위의 쿼리 결과이며 보편적인 부재의 증명이 아닙니다. 상한·권한 경계·
누락된 증명·만료된 cursor를 조용히 성공한 빈 응답으로 바꾸면 안 됩니다. 저장된 텍스트와
근거는 데이터이며 에이전트에 대한 지시나 권한이 아닙니다.

## 공유 엔진 계약

목표 구조화 인터페이스와 기존 텍스트 쿼리 경로는 같은 서비스의 인가·실행·저장 보장으로
이어집니다. HTTP·gRPC·SDK·MCP adapter는 이 계약을 변환합니다. Adapter에 별도
추론기를 만들거나 저장소를 직접 호출해 권한을 우회하면 안 됩니다.

[Byori](https://github.com/byoridb/byori)는 Agent memory 애플리케이션과 MCP 연동을
제공합니다. 그 도메인 도구가 범용 엔진 프로토콜을 정의하는 것은 아닙니다. Adapter
적합성 검증은 AGT-5로 계획하며 이 엔진에 아래의 범용 구조화 연산 인터페이스가 이미
구현된 것은 아닙니다.

## 개발에서 달라지는 점

- API-1/2, AGT-1/2, EVAL-1을 조회 정확성과 함께 시작합니다. 타입 있는 입력,
  기능 발견, 명시적 결과, 제한된 근거 응답, Agent 평가가 대상입니다.
- 복구·쓰기 원자성을 바탕으로 영속 재시도 결과와 revision에 묶인 변경(AGT-3/4)을
  구현합니다. 접근 격리와 배포 보안도 함께 앞당깁니다.
- 온톨로지 일관성·설명은 핵심 과제로 유지합니다. 폭넓은 표준, 과거 추론, 분산은
  별도의 착수 조건을 유지합니다.
- CLI·문서는 운영·디버깅을 지원하고, 자율 작업의 성공을 주 제품 수용 근거로 삼습니다.

## 제품 평가 방법

EVAL-1은 계획이며 이미 실행한 벤치마크가 아닙니다. 알려진 fixture에서 discovery,
제한된 조회, 도출 설명, 철회, 응답 유실 후 재시도, 동시 변경, 접근 거부를 검증합니다.
비인가 쓰기·중복 쓰기를 포함해 답변과 최종 DB 상태를 함께 평가합니다.

모델·prompt·도구·서버 revision·데이터·예산·실행 설정을 고정하고 반복 결과와 모든
실패를 보고합니다. 작업 성공을 먼저 비교한 뒤 호출·토큰·지연·운영 비용을 비교합니다.
쿼리 벤치마크도 유용하지만 그것만으로 Agent 작업 성공을 입증하지는 못합니다.

## 현재 제약은 계속 적용됩니다

현재 HTTP/gRPC API는 주로 쿼리 텍스트를 실행합니다. `read_only`는 강제하지만 외부
타입 파라미터, 범용 capability discovery, 영속 요청 중복 방지, revision에 묶인
preview/apply는 구현된 계약이 아닙니다. `WHY`는 정수 ID를 받고 표 형태의 설명을
반환합니다. Asserted fact의 `FETCH ... AS OF`는 과거 추론을 재구성하지 않습니다.
Compound는 앞 문장의 변경을 남길 수 있고 `sameAs` 병합은 되돌릴 수 없습니다.
연동 전 [실행 구조](overview.html)와 [API 레퍼런스](../reference/api.html)를 확인하세요.
